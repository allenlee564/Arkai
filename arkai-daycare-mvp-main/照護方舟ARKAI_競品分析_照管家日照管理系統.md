# 照護方舟 ARKAI — 競品分析：照管家日照管理系統

> 日期：2026-07-07  
> 對象：照管家 日照管理系統（常誠電腦股份有限公司）  
> 目的：分析照管家對 ARKAI 的競爭意義，釐清功能重疊、差異化定位與 MVP 取捨。

---

## 0. 結論先行

照管家是 ARKAI 的直接競品，但它主要站在「日照行政管理 SaaS」位置，而非「地端 AI 照護決策 / 即時預警平台」位置。其強項是成熟的日照營運電子化（紀錄、支審核銷、評鑑、排班、交通接送等）。

ARKAI 不應正面複製照管家的完整行政 SaaS。更好的定位是：

> 照管家把日照中心紙本行政電子化；ARKAI 把日照中心的照護資料變成地端即時判斷與自動生成紀錄。

因此，ARKAI 的競爭主軸不該是「我也有表單」，而是「我能在機構內完成 AI 推理、即時預警、SOAP / 聯絡簿草稿生成，且 PII 不出機構」。

## 3. 照管家功能拆解

### 3.1 官方頁面主打能力

官方頁面主打四大區塊：**全面照顧管理**（照顧日誌、生命徵象、照顧計畫、配合評鑑）、**高效行政管理**（減少核對、加速支審核銷、家屬手機/平板掌握）、**全面紀錄與評估**（每日紀錄、自立訓練、計畫評值追蹤）、**科技輔助照護**（資訊整合、設備介接）。細項與差異化對照見 §3.2、§4。

### 3.2 重點功能圖拆解

| 模組 | 照管家功能 | 成熟度推論 | ARKAI 對策 |
|---|---|---|---|
| 操作介面 | 個別化操作介面、個別化角色設置、直覺式個人功能、簡單易學好操作 | 基礎 SaaS 能力成熟 | ARKAI UI 必須更少步驟，不能比既有 SaaS 更難 |
| AI 生理量測 | 五合一量測儀器、儀器與系統連結、自動檢測值上傳、生理指標值監測 | 偏量測整合與數值上傳 | ARKAI 要主打連續感測、趨勢、閾值、預警，而非只是上傳 |
| 經營管理 | 人事管理、會議管理、排班管理、考勤管理 | 行政營運能力強 | MVP 先避開，除非合作機構要求最小欄位 |
| 照護管理 | 照護評估與處遇、督導服務管理、健康生活照顧、服務品質監測 | 與日照照護流程高度貼合 | ARKAI 以 AI 草稿與戰情牆補強，不複製整套後台 |
| 財務管理 | 支審請款作業、自費收費管理、薪資作業管理、管理統計報表 | 照管家防守區 | ARKAI 初期不碰財務主流程，只輸出可支援核銷 / 成效證明的資料 |
| 專車接送 | 車輛管理、派車管理、智慧里程數計算、BD03 支審導出 | 垂直日照營運功能 | 非 ARKAI MVP 核心，跳過 |
| 家庭聯絡簿 | 家屬聯絡資訊、個案活動紀錄、個案生理紀錄、家屬叮嚀服務 | 已有電子化能力 | ARKAI 差異化在「自動生成家屬版草稿」 |
| 評鑑管理 | 個案權益保障、專業照護品質、經營管理效能、安全環境設備 | 強貼合機構評鑑 | ARKAI 可提供感測與 AI 紀錄作為評鑑佐證資料 |

## 5. 照管家的強項

### 5.1 行政完整度高

照管家涵蓋支審請款、自費收費、薪資、排班、考勤、交通接送、評鑑——都是機構容易買單的剛需，不是展示用。**提醒**：別低估行政剛需，機構負責人每天先痛的是人力不足、核銷麻煩、評鑑壓力，AI 再漂亮也排在後面。

### 5.2 很貼近現場語言

照管家的文案不是科技感敘事，而是「操作易學」「管理簡單」「減少人員負擔」「支審核銷」「家庭聯絡簿」。這些語言貼近日照中心採購者，不需要教育市場。

對 ARKAI 的提醒：對外不能只講 edge AI、egress、NER。要翻成現場語言：

| 技術語言 | 現場語言 |
|---|---|
| 地端 AI 推理 | 個資不出機構也能自動寫紀錄 |
| egress 閘道 | 出去前先幫你把個資擋掉 |
| 感測串流 | 長者狀況不用等人手動補登 |
| SOAP 生成 | 照服員講完，護理紀錄先幫你打好草稿 |
| 趨勢預警 | 出事前先提醒，而不是出事後補紀錄 |

### 5.3 電子家庭聯絡簿已是標配

照管家已有家屬手機/平板掌握狀況的電子聯絡簿。ARKAI 不能只說「我們也有」，要說：

> 既有系統是電子聯絡簿；ARKAI 是**自動生成**聯絡簿草稿，把生理趨勢、活動、情緒事件整理成家屬看得懂的版本。

### 5.4 評鑑與核銷能力形成採購防線

機構採購不只看照護體驗，也看能否支援評鑑、核銷與報表，照管家在此敘事成熟。**提醒**：MVP 可不做完整核銷，但輸出要能當評鑑佐證——如長者活動量趨勢、異常事件處理時間、SOAP 確認率、聯絡簿發布率、自立訓練成效（佐證是否被評鑑採認見 §11-Q6）。

## 6. 照管家的可攻擊點

> 以下皆為「公開頁面未明確主打」的推論，非「產品沒有」；下結論前需 demo/訪談驗證（見 §11）。

### 6.1 AI 深度不明

功能圖有「AI 生理量測」，但描述偏量測儀器整合與數值上傳，未明確展示生成式 AI、語音轉 SOAP、防幻覺來源標註。**攻點**：不是「記錄生命徵象」，而是「用生命徵象生成可追溯的護理紀錄」。

### 6.2 即時預警閉環不明

有生理監測，但未明確主打離床超時、跌倒、夜間異常、戰情牆、斷網仍可預警的閉環。**攻點**：機構需要在風險變事故前先看到，不只是記錄。

### 6.3 資安差異化敘事不足

未明確主打 PII 不出機構、地端推理、去識別封包、egress 稽核、mTLS、設備金鑰。**攻點**：對在意個資的機構，ARKAI 是機構內地端閘道，不是雲端 SaaS——這是唯一雲端 SaaS 結構上難跟進的攻點（見 §8.1）。

### 6.4 行銷頁維護訊號偏舊

日照頁優惠日期止於 2024/05/31（查閱日 2026-07-07）——只是行銷頁維護訊號、不代表停更，但顯示其對外溝通未強打最新 AI/地端/資安趨勢，ARKAI 用新敘事切入較易顯前沿。

## 7. ARKAI 的定位建議

### 7.1 不建議定位

不要把 ARKAI 說成「照管家 + Jubo AI 紀錄 + AIoT 監測」的功能拼盤——會被追問「那對手為什麼不能各自補齊？」，護城河立刻失守。

### 7.2 建議定位

> ARKAI 是日照中心的地端 AI 照護決策層。它不取代所有行政 SaaS，而是把感測資料、語音紀錄、開案評估先在機構內轉成可行動的預警、SOAP 草稿、家屬聯絡簿草稿與去識別趨勢。

### 7.3 對照管家的銷售話術

| 客戶說法 | ARKAI 回應 |
|---|---|
| 我們已經有照管家了 | 很好，照管家處理行政與紀錄；ARKAI 補的是地端 AI 預警與自動生成草稿 |
| 我們不想換系統 | ARKAI 初期不用取代既有系統，只先做戰情牆、SOAP 草稿、家屬聯絡簿草稿輸出 |
| 我們擔心個資上雲 | ARKAI 的核心就是 PII 不出機構，出去前只送去識別趨勢 |
| 我們人手不足，沒空多用一套 | ARKAI 的價值是少打字、少巡查、少補登，不是多一個後台 |
| 既有系統也有生命徵象 | ARKAI 的差別是把生命徵象接到預警與紀錄生成，而不是只存成欄位 |

## 8. MVP 取捨建議

### 8.1 應該做

「性質」欄的用途：分清哪些是**抄不掉的架構護城河**、哪些只是**暫時領先的功能**（Jubo / 照管家下一版就能加）。賭注要壓在前者；後者是入場券，不是護城河，別當差異化主軸賣。

| MVP 能力 | 為什麼要做 | 性質（可複製性） |
|---|---|---|
| 開案風險 / 成本初篩 | 避開照管家的行政表單戰，直接輸出決策 | 中（規則可抄，但需臨床校準資料） |
| 智慧照護戰情牆 | 把紀錄系統升級成即時狀態系統 | 易複製（UI 層，暫時領先） |
| 離床 / 跌倒預警 | 照管家公開頁面未明確主打，是 ARKAI 的清楚差異 | 易複製（Jubo/AIoT 可加，暫時領先） |
| 語音轉 SOAP 草稿 | 對日照現場行政負擔有直接省時效果 | 易複製（Jubo 已有，暫時領先） |
| O 欄自動帶入實測值 | 建立「AI 不亂編」的可信度 | 中（防幻覺設計，可抄但需用心） |
| 家屬聯絡簿自動草稿 | 對照照管家的電子聯絡簿，做高一層自動化 | 易複製（暫時領先） |
| **地端 NER / PII 遮蔽展示** | 把資安護城河具象化 | **難複製（架構級：雲端 SaaS 要抄需棄雲）** |
| **去識別 egress log** | 讓「個資不出機構」可驗收、可稽核 | **難複製（架構級護城河）** |

### 8.2 先不要做

| 暫緩能力 | 原因 |
|---|---|
| 完整排班 | 照管家已成熟，MVP 不該陷入行政後台戰 |
| 薪資計算 | 高規則複雜度，且不是 ARKAI 差異化核心 |
| 交通接送 / BD03 | 日照營運很重要，但會拖慢 MVP |
| 完整支審請款 | 先輸出佐證資料即可，完整核銷後續再接 |
| 完整評鑑管理 | 先提供 AI 紀錄與趨勢作為評鑑資料來源 |

## 9. 競爭策略

### 9.1 灘頭市場

先打的不是所有日照中心，而是：**對雲端個資風險敏感**、已有基本行政系統但仍被紀錄/巡查/家屬溝通壓垮、願意用手環/床墊/雷達做場域驗證、想用科技改善評鑑或補助材料的機構。

### 9.2 合作而非替換

短期銷售不應說「替換照管家」。更好的策略是：

> ARKAI 先作為照管家等既有系統旁邊的地端 AI 層，輸出可貼回既有紀錄系統的 SOAP、聯絡簿與事件摘要。

這可以降低客戶導入阻力，也避開成熟 SaaS 的資料遷移與流程替換成本。

**⚠️ 但這裡有一個必須先講死的邊界**：若照管家（或客戶既有系統）是**雲端 SaaS**，把含臨床內容/PII 的 SOAP、聯絡簿「回寫」進去，等於**這些個資透過整合離開了機構**——直接和 ARKAI「PII 不出機構」的護城河打架。也就是說，**回寫策略的可行性完全取決於既有系統的部署型態（見 §11-Q3：雲端 / 地端 / 混合）**，這不是一般待確認事項，而是決定 §9.2 能不能成立的前置條件。三種收法擇一講死：

1. **只回寫去識別摘要**（不含可重識別 PII），完整紀錄仍留 ARKAI 地端；或
2. **僅在既有系統有地端版、資料仍在機構內時**才回寫；或
3. 明確界定「客戶既有 SaaS 本來就存這些 PII，ARKAI 的回寫沒有擴大外流面」——但這條會弱化資安敘事，需審慎。

在 §11-Q3 未釐清前，對外一律以「輸出留地端、可匯出去識別摘要」為預設說法，不承諾直接回寫雲端系統。

### 9.3 長期平台化

長期護城河不是單一功能，而是成為機構內的地端去識別化閘道：感測設備先接 ARKAI → 含 PII 資料一律地端處理 → 只有去識別趨勢可上雲、外送全留 egress log → 既有 SaaS 要資料時由 ARKAI 提供處理後安全可控的輸出。

## 10. 可直接放進簡報的說法

**30 秒版**：照管家已把日照行政流程電子化（支審、評鑑、照護紀錄、家屬聯絡簿、排班、財務）。ARKAI 不打完整後台，而是補上它公開頁面未明確主打的地端 AI 層：感測即時預警、語音轉 SOAP、聯絡簿自動草稿，以及 PII 不出機構的去識別閘道。

**投資人版**：既有日照 SaaS 的護城河在流程完整度；ARKAI 的切入點不是重做後台，而是用地端 AI 與感測資料建新的資料處理層。當機構越在意個資不上雲、即時預警與 AI 紀錄自動化，ARKAI 先作為旁掛層導入，再逐步成為機構內 IoT 與照護資料的去識別化標準閘道。

## 11. 待補強問題

1. 照管家是否已有實際 AI 生成紀錄能力？公開頁面未明確顯示，需 demo 或訪談確認。
2. 照管家是否支援即時警報？若有，需確認是量測異常通知，還是離床 / 跌倒 / BPSD 趨勢預警。
3. 照管家資料部署型態是雲端、地端、混合，或可客製？公開頁面未清楚說明，需銷售訪談確認。**（決定 §9.2 旁掛回寫策略是否會破壞「PII 不出機構」，優先釐清。）**
4. 照管家是否有 API 可讓 ARKAI 輸出 SOAP / 聯絡簿草稿回寫？若可整合，ARKAI 可採「旁掛 AI 層」策略；但回寫內容須符合 §9.2 的邊界（去識別摘要 / 地端限定）。
5. 日照中心真實採購決策中，支審核銷與評鑑權重是否高於 AI 預警？需用場域訪談驗證。
6. 台灣日照評鑑實務上，是否接受 AI 紀錄、感測趨勢等衍生指標作為評鑑佐證？§5.4／§8 多處假設可當佐證，此假設未驗證，需查評鑑基準或訪談確認。
